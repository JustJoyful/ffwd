### Continue-gates (decide when to proceed, never what is reported)
- **Teacher pilot to bulk:** cache-hit ratio >= 60%, and the kept-rate gate below. The kept-rate gate is **owner-approved as `max(40%, X1_dev - 15 pp)`** (17 Nov 2026); the number is written here once the X1 dev run exists (approved at <= $0.05, after the terms file is in place). Rule: kept-rate on the pilot must be at least `max(40%, X1 dev success - 15 pp)`. Reasoning: with rejection sampling the kept-rate is about the teacher's pass rate on train-style tasks, which X1 on dev estimates; a pilot far below that signals a prompt, format or checker bug rather than a hard task mix; and the absolute floor 40% keeps the cost per kept trajectory below 2.5x the budget plan's (which assumed 70%). The computed number is written here before any bulk spend. **Computed 19 Nov 2026: X1 on 60 dev tasks (first 60 by task id, frozen prompt v1, spec-first, thinking off) = 58/60 = 97% [89%, 99%], cost $0.0423 (`reports/2026-11-19-x1-dev/X1-deepseek-v1-dev60`); gate = max(40%, 97% - 15 pp) = **82%**.** The pilot also needs the 10 hand-read trajectories to show no format or checker problems (owner condition, 19 Nov 2026).
- **SFT to GRPO:** GRPO starts only if M1 reaches >= 60% dev success with <= 5% invalid actions. **If M1 reaches >= 90% on dev, the report says "SFT nearly sufficient" (little headroom left for GRPO) and GRPO still runs as preregistered**; the claim about GRPO's gain is then bounded by that headroom.

### GRPO stopping rules
Cap 15 GPU-hours; stop if the no-signal group share exceeds 60% for 10 consecutive steps, if the refusal rate on supported tasks leaves `REFUSAL_RATE_BAND`, if the invalid-action rate rises for 10 steps, or if a human spot-check finds an exploit (then fix the reward in a new commit and restart from the last clean checkpoint, documenting the discontinuity).

### Controls and disclosures
Shuffled-reward run (30 steps; must not improve dev). Leakage audit (`eval/leakage.py`) of test-phrasing and test-compositional against train must stay below `LEAKAGE_JACCARD_MAX`. 50 random passed M3 outputs are inspected by hand. Single training seed unless compute allows more; the report says "single seed". B0 is hand-written by the same author as the tasks (process control: B0 v2 is written from the train phrase banks only and its source is checked not to reference the held-out module). The `context_first` and `indirect` styles reuse train symptom/core wordings inside a new framing, so test-phrasing measures robustness to framing and situation context, not to entirely new vocabulary. Teacher and X1 are the same model family. Checker blind spots: filter-made A/V offsets, first-frame rotation measurement, and no default quality floor on trimmed/reframed size tasks (D-025).

## Phase 4 addendum: test-real (design fixed 22 Nov 2026, before any test-real request exists; Phase 1 does not use it)
test-real measures the real thing: real clips and requests the owner wrote by hand. It is **not part of the Phase 1 family, report or exit criteria** (Amendment 3, item 8), and nothing in it can change a Phase 1 result. It is run once, under the test lock, after its task file is frozen. Mechanics (commands, CSV columns, the rules for writing requests) are in `eval/test-real/README.md`; this section fixes the design and the analysis.

1. **Size and composition.** About 100 requests on **at least 6 test-real clips** (registered with `--role test-real`; excluded from every training, dev, taskgen and app path; CI guards it, `tests/taskgen/test_clip_roles.py`). **Family quotas** (a request counts toward every family it needs): at least 6 requests for each of F1, F3, F4, F5, F6, F9, F10 and F12, and at least 3 for each of F2, F7, F8 and F11; about half single-chore, the rest two or three chores. **At least 30 requests are copy-eligible** (a stream copy is a correct answer; the rule and the mix are in the README, item 3b). About 10 are `ambiguous` or `unsupported` and stay in the denominator. Gold specs are made from the owner's plain-words expected outputs and **shown to the owner for approval**, and each reference solution must pass its gold spec (a failing reference is a task bug fixed with the owner, never silently dropped); the sha256 of the frozen task file is recorded here before anything is run.
2. **Systems evaluated: the FROZEN Phase 1 GGUF Q8_0 models**, exactly as in the Phase 1 test run: B0, B2, M1, M3 (and X1 only if the DeepSeek ledger still allows it under its cap, otherwise not run). Their file sha256 values are in the Phase 1 report manifest. Any browser MLC model, and a Q4_K_M row if the shipped native format differs, is an **extra row**, labelled, never a replacement. No model, prompt, checker or metric is changed for test-real.
