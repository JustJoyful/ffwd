- **iGPU: the output is numerically broken, not just slow.** The replies on the Intel adapter were gibberish ("依旧依旧constconst,,,,,"), so every episode ended at the turn budget with invalid actions. Cause unknown. I started a diagnostic (f16 KV cache against q8_0 + flash attention; llama.cpp warns flash attention runs on the CPU on this backend): result below when it lands. **Product implication (my recommendation, not built):** never trust WebGPU blindly; at model load run a tiny canary prompt with a known expected reply and fall back to the processor path on a mismatch, and say which path is in use (the path notice already does). The honest wait message must also cover a slow GPU.
- **CPU: thread choice matters a lot.** Pinned to 4 P-core threads it ran at 36 tok/s (3.2 s median); my first CPU run (wllama's default 6 threads on this 12-thread hybrid CPU, with other load around) gave 17 tok/s and 6.8 s. The measured waits in the app's CPU notice (10 s first step, 6 s later) came from that slower run, so they are pessimistic for a well-pinned run; they were left unchanged until more machines are measured. A thread default such as min(4, cores/2) is worth testing.
